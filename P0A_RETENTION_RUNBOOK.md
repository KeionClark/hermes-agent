# P0a restricted Kanban event retention (release gate)

Decision source: Keion's 30 Sep 2026 scoped approval on Kanban card `t_855cbdd1`. This implementation is **dark** until the Release Engineer integrates and independent QA accepts the **new exact SHA**. It does not change the canonical board, send messages, spawn workers, or backfill events.

## Contract

`hermes_cli.kanban_event_retention.purge_expired` deletes rows with `created_at < now - 30*86400` from `hermes_events` and rows with `enqueued_at < now - 30*86400` from `hermes_router_inbox`, in bounded batches under `BEGIN IMMEDIATE`. An inbox row referring to an expired event is deleted even if recently enqueued. Failure/deadletter rows referring to deleted event IDs are removed in the same transaction. Existing cursors are not rewound, reset or blocked: polling traverses the remaining events by monotonic ID; an expired unacknowledged event is not replayable. Each transaction rolls back in full on failure. Strictly on the cutoff is retained. `task_events`, notifier/history, tasks and unrelated rows are untouched. An event idempotency key can be reused after expiry, but the new row gets a new (AUTOINCREMENT) ID.

The finite opt-in runner (`python -m hermes_cli.kanban_event_router`) purges before **every** routing iteration and fails closed instead of routing if its configured bounded budget leaves a possible retention backlog. `--purge-only --board-path /absolute/approved/board.db` runs explicit maintenance without a subscriber, routing, or worker spawn. `--retention-batches N` controls the bound (default 100, each batch up to 500 per table); an exhausted budget exits nonzero. Run again rather than disabling the cap. A scheduled invocation of this command is REQUIRED for deletion when the router is not running; operator should configure and verify at least hourly on the approved board as a no-agent local maintenance job, monitor nonzero exits, and read back counts/oldest timestamps. A timer alone is not proof of retention. No schedule is installed by this branch; production activation is blocked until release configures and verifies it.

## Access and activation

The CLI refuses an absent board and requires a regular DB and parent directory, each owned by the invoking account and inaccessible to group/other (`0700` private directory, `0600` DB); symlink at either leaf or immediate parent is rejected. Private parent protects SQLite WAL/SHM and backups made there. Run under the restricted Hermes Unix identity, not a shared home or web-server public path. Review ACLs, ancestor traversal and any replicas/backups separately. Only canonical card lifecycle interests (`card.created`, `card.blocked`, `card.completed`, `card.status_changed`) may be selected via CLI; choose the minimum needed for the blocked-card resolver (typically status_changed and blocked). Low-level event bus remains a generic internal API and is not a security boundary against Python code running as the same Unix user. Never expose raw DB/CLI to a broader user or network service.

Release: reconcile the builder commit on current local main; independent exact-head QA and project ruling; disposable old/new board migration and age-boundary drill; review existing canonical board file, directory, ACL and backup policy before any chmod; make a scoped backup under a private directory with documented expiry (a backup with patient-linked identifiers must not silently outlive the approved window). Configure explicit hourly maintenance and bounded router only after privacy and QA gates; read back oldest event/inbox age and repeat after restart, and perform only the separately authorized synthetic non-patient TEST-board transition. Canonical activation requires read-back of fresh inbox effect and event-to-router latency. Rollback: disable runner/timer and revert code by ordered release path; disabling does NOT delete already stored identifiers, so keep maintenance working and verify expiry through rollback. If cleanup fails, pause routing, retain the card open, fix the failure and rerun; do not claim compliant deletion. Historical `task_events`, snapshots, WAL frames, filesystem backups, or downstream copies are **not** purged by this routine: release must inventory and separately apply the approved retention policy to any new copies, without purging pre-existing task history beyond Keion's authorization.
